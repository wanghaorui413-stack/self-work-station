# 0001 提醒由电脑上常驻的工作台发出，数据留在本机，不加后端

- 状态：已接受
- 日期：2026-11-01

## 背景

工作台要提醒用户面试、测评等招聘事项的时间点。用户每天都用电脑，不需要手机提醒。原项目是纯静态、local-first 的单页应用：提醒靠浏览器 Notification API，页面一关就失效；数据也只存在 localStorage 里，外部程序读写不到。

## 决定

- 由**电脑上常驻的工作台**发出提醒（Windows 系统通知）。本地小服务器（`scripts/serve.mjs`）开机后自动启动，工作台以 Edge 应用的形式常驻。
- **读邮件、提取事项**交给 Claude 定时任务，每天 8:30、18:30 各跑一次：163 邮箱自动转发到 Gmail，定时任务读取 Gmail，再通过 Claude 桌面端把事项写进本机的 `data/items.json`。
- 招聘事项数据**只存在本机**的 `data/items.json`，不提交到 Git，也不上传到任何云端存储。工作台通过本地服务器的 `/api/items` 读写这个文件。
- 排程和提醒都在网页里计算；定时任务只负责“邮件 → 事项”。

## 考虑过的其他方案

- **手机日历订阅 .ics**（小米手机需借助 ICSx⁵）：存放 .ics 的 Gist 域名在国内不稳定，同步失败时用户察觉不到；用户本身也不需要手机提醒。
- **私密 Gist 作为数据中转**：Claude 会话的 GitHub 权限只覆盖关联的仓库，访问 Gist 的接口会被拦截（403）。要绕过只能把个人 token 写进定时任务配置，风险太大。
- **私有 GitHub 仓库作为数据中转**：网页仍然需要 token，而且没法确认每次新开的定时任务会话都能拿到写权限。
- **本地脚本直接用 IMAP 收 163 邮件**：数据完全不出本机，但事项提取只能靠规则匹配，质量不够。
- **自建后端，推送到微信**：需要常驻服务和运维，打破零后端的定位。

## 后果

- 定时任务运行时，电脑和 Claude 桌面端必须开着。错过的那次由下一次补上：每次都回查近 3 天的邮件，并按邮件 id 去重。
- 电脑关机或工作台没运行时，不会有提醒；开机后，还没过期的提醒会补发。
- 招聘邮件会多存一份在 Gmail 里（经 163 转发）。
- `data/items.json` 由两方写入，靠字段分工（见 `docs/recruiting-data.md`）和本地服务器的串行写入来避免互相覆盖。
